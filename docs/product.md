# SeminarRoom 产品与设计说明

## V1.2 正式设计基线（2026-11-08）

长期产品是 **AI Research & Collaboration Workspace**：AI团队围绕目标自主分工与协作，用户可观察、干预、审批和控制，成果可核验、编辑与交付。教学研究是第一个应用。完整定位、对象边界与工作流以[阶段0基线](stage0-v1.2/README.md)及[执行契约](stage0-v1.2/user-workflows.md)为准；下文保留当前Alpha取舍和历史说明，不能将其固定三角色视为长期团队上限。

阶段1真实Project→Session→Output；阶段2国内多模型与持久身份（紧接阶段1）；阶段3自主任务分工/交接/恢复；阶段4共同研究/证据审查/写作；阶段5长期记忆/工具/事件驱动与自主运行。本次不实现这些生产功能。

## 1. 一句话

SeminarRoom 把一段材料变成一场可参与、可暂停、可核对引用的 AI 研讨课；重点不是生成漂亮的课堂内容，而是让“主持人决定下一步、两位参与者独立回应、用户随时打断、每个引用可回到原文”这条交互链真实发生。

## 2. 用户场景

### 当前定位：早期可用版（Alpha）

**教学研究是 SeminarRoom 的第一个内置产品**，当前通过材料、三问、三角色研讨和总结导出这条通用流程，服务教学备课与方案比较；尚没有独立的教学研究模板或专用模块。

多 API Key、多模型协作、自主分工、共同研究与写作、界面优化是未来发展方向，尚未实现或验收。当前的主持人调度是既定角色内的发言安排，不代表 Agent 已能自主组建团队、分解研究任务或联合写作。

### 首个真实教学研究案例

2026-11-07，使用千问 `qwen-plus`（`dashscope.aliyuncs.com`）完成书法教学备课研讨：“一节90分钟毛笔书法入门课，如何兼顾看清示范、动手练习与个别反馈？”实际运行 **6轮、14次模型调用、42,495 tokens**（输入37,444，输出5,051），包含用户插话、参与者直接回应、独立总结、人工编辑保存及 Markdown / JSON 导出。

案例材料为助手自拟的备课情境，不是实际课堂数据。三问经人工编辑，讨论中有人为插话干预，最终总结也经人工校订；不能将演示结果视为自主教学研究能力或教学效果证据。这是一次人工操作的真实运行案例，不等于 `npm run check:live` 自动化实模验收通过；目前仍未生成该脚本的 `docs/live-run.json` 报告。案例没有验证真实模型下的暂停/继续、长期稳定性、教学效果或多模型协作。三角色使用同一个模型和同一套服务配置，通过独立上下文分别调用。

### 主要用户

- 需要带学生读一份短材料、但不想只做单向讲解的教师/助教；
- 想在讨论前快速看清材料中的分歧、证据缺口和未解决问题的小组组织者；
- 想验证“多 Agent 讨论是否真的在协作”的开发者/研究者。

### 典型任务

用户粘贴一份某学生共学空间的试运行记录，主题是“是否应把周五最低开放时长延长到 24:00”。材料里有签到比例、问卷结果、值班成本、管理方案和双方意见。用户希望：

1. 先得到三个值得讨论的问题；
2. 看到两个不同视角围绕材料互相质疑，而不是重复同一段话；
3. 在讨论中途追问“如果只延到 23:00 呢？”；
4. 结束后得到能核对的共识、分歧、材料依据和未解决问题；
5. 保存下来，刷新后还在，并能导出。

### 非目标

- 不生成课件、视频或语音；
- 不做多人实时课堂/云同步；
- 不做通用文档问答知识库；
- 不用模拟讨论代替事实核查；
- 不追求“一个大平台”，只把一条研讨主路径做完整。

### 从 OpenMAIC 观察到什么

- OpenMAIC 是 MIT License（Copyright (c) 2026 THU-MAIC），见 [LICENSE](https://github.com/THU-MAIC/OpenMAIC/blob/main/LICENSE)。README 说明其根目录 MIT 许可，但个别随仓库打包的第三方包有各自许可；SeminarRoom 不复用这些包。
- 它把材料转成多 Agent 课堂：教师/同学 Agent、幻灯片、测验、交互模拟、PBL、白板和 TTS；支持材料上传、解析、检索和导出。
- 其 Key Architecture 明确写到 **Multi-Agent Orchestration (`lib/chat/pi/`) — Server-side Pi director loop that hands each classroom turn to agents through `call_agent`**。这与“先写一个完整剧本再播放”相反：导演在服务端逐步决定把发言交给谁。
- 材料使用：支持上传、解析、文本检索、媒体复用；角色可以在课堂中引用材料。课堂记录和导出也是产品的一部分。
- 它面向的是完整课堂平台，包含 PostgreSQL、队列/租约、TTS、ASR、渲染服务、PPTX/HTML 导出等大量基础设施。

### 借鉴了什么，没有借鉴什么

**借鉴的产品机制：**

- 主持人是独立的“导演”，每一步决定下一步动作，而不是由一次调用生成全部台词；
- 角色有各自的上下文/分工，发言按结构化交接；
- 材料编号、工具读取、引用回到原文；
- 讨论记录与技术记录分开呈现；
- 控制轮次、预算、暂停和结束。

**没有照搬：**

- 没有复制 OpenMAIC 的源码、提示词、UI 资源或数据库结构；
- 没有实现幻灯片、白板、TTS、ASR、PBL、联网搜索、视频导出、多人账户；
- 没有引入 PostgreSQL、对象存储、队列、渲染服务；
- 没有把“教师/同学”完整课堂角色体系压扁成同一套话术。

SeminarRoom 是独立实现的小型研讨应用，不是 OpenMAIC 的改名分支。

## 4. 核心设计

### 4.1 三个独立上下文

| 角色 | 上下文内容 | 输出 |
| --- | --- | --- |
| 主持人 | 主题、三问、角色表、材料索引、最近讨论、未回应用户消息、进度/预算 | `HostAction` JSON |
| 参与者 A | 自己的席位与任务、相关材料段落、自己的近期发言、近期讨论、待回应用户/近期对象 | `blocks + citations + addresses + stanceUpdate` JSON |
| 参与者 B | 同上，但席位不同（检验派），视角不同 | 同上 |
| 总结员 | 完整讨论 + 相关材料原文 | 共识/分歧/依据/未解决 JSON |

每次模型调用都重新组装上下文，不存在“三个角色共享一条 messages 数组”的伪独立。技术记录为每次请求保存上下文指纹（`contextHash`），用于说明它们不是同一上下文的复制。

参与者不会拿到主持人的系统提示或另一参与者的系统提示；他们会看到必要的公开讨论片段。这样既保持独立，又能互相回应。

### 4.2 编排状态机

```
draft
  ├─ planQuestions() → 3 questions（可编辑）
  └─ start()
        ↓
      running ── pause() ──→ paused
        │                      │
        │                      └─ resume()
        │
        ├─ host turn
        │    ├─ invite/clarify → participant turn → round++
        │    ├─ end → ended
        │    └─ 待用户消息 → 必须安排 direct response
        │
        ├─ round >= maxRounds → ended
        ├─ role call budget exhausted → ended (call_limit)
        └─ API/结构错误 → error ── retry() → running
                                    └─ end() → ended
```

`ended` 之后只有独立的 summary 调用，不再有 host/participant 调用。

### 4.3 用户插话优先

用户消息写入 `pendingUserMessageIds`。主持人输出的 `addressUserMessageIds` 必须包含所有待回应用户消息；否则服务端拒绝这次主持决策并要求修复。参与者被要求：

- 在发言中先直接回应；
- 在 `addresses` 中列入用户消息 ID；
- 服务端将其标为 `directToUser=true`，界面显示“直接回应你”。

如果用户暂停时发话，消息先排队；继续后主持人必须先处理，不得恢复原来的发言顺序。如果用户插话正好撞上进行中的主持调用，服务端会在下一次主持调用前检测到新的 pending，并重新安排。

### 4.4 主持人的真实决策

主持人每次只返回一个 JSON 动作：

- `invite`：点名一位参与者，给出公开主持语、具体任务、聚焦点、要回应的近期消息；
- `clarify`：要求澄清；
- `end`：说明结束理由。

服务端不预置“第 n 轮固定问什么”。硬规则只负责产品约束：

- 有用户插话时先回应用户；
- 两位参与者都要至少发言一次，不能提前结束；
- 开场前两轮不要连续只点同一人（除非先处理用户插话）；
- 达到轮次/调用上限就停止。

这些规则在 `server/seminar.ts` 的 `validateHostReferences` 中执行，不靠 UI 动画。

### 4.5 材料与引用

材料被编号为用户可见的段落，参与者和总结员必须使用段落编号 + 逐字引文。服务端验证：

1. 段落编号存在；
2. 引文是该段落原文的连续子串；
3. 引文不是省略号拼接；
4. `background` 块不允许带材料引用；
5. 声称“材料证据”但没有任何合法引用的块会降级为“观点”。

无效引用不会静默保留。界面显示“有引用未通过逐字核对，已隐藏”，技术记录保留警告。这样实现的是“可核对”，不是“看起来像引用”。

### 4.6 总结与可编辑性

总结员单独调用，不继续扮演角色。总结结构：

- 共识；
- 分歧；
- 材料依据（段落 + 逐字引文 + 说明）；
- 未解决问题。

总结中的依据再次做逐字核对。用户可以编辑文本和依据说明；引用本身保持不可随意改写，避免“编辑后引用失真”。编辑后保存到会话，导出直接读取保存后的状态。

### 4.7 失败、预算与控制

- 每个请求记录 `status`（ok / error / aborted）、HTTP 状态、耗时、token、工具调用、错误摘要；
- 结构校验失败允许一次修复调用，仍失败即进入 `error`；
- 失败会显示错误横幅，不能显示成成功；
- 结束会 abort 进行中的请求；
- `SEMINAR_MAX_CALLS` 包含问题生成、工具续调、修复、总结在内的所有请求；
- 角色调用预算预留一次总结调用；
- 输出 token、超时、轮次均可配置；
- 不估算费用；只显示接口返回的 token。

## 5. 资料与安全

- API 密钥只从服务端环境变量读取；`.env.local` 被 `.gitignore` 忽略；
- 浏览器不会收到密钥；
- 技术记录不保存提示词、响应体或 Authorization；
- 错误文本做基本脱敏；
- 服务只绑定 `127.0.0.1`；没有为公网部署做认证/限流；
- 会话和材料保存在本地 `data/sessions/*.json`；
- 示例回放和真实运行在 UI 中分开标注；
- 示例材料全部为虚构测试文本，不用于事实断言。

## 7. 关键取舍

### 为什么用本地 JSON，而不是数据库

本项目是单用户、本地运行的早期可用版，目标是让 Codex/用户可以一条命令安装；引入 PostgreSQL 会显著增加部署成本。代价是没有并发控制、权限和云同步。会话写入串行化，并在每次状态变化保存，足够覆盖刷新恢复与导出。

### 为什么用轮询，而不是 SSE

服务端编排是异步任务，UI 只需要观测状态。1 秒轮询实现简单、刷新恢复容易、断线后自动重连；代价是延迟和额外请求。SSE 会作为后续优化，而不是核心正确性的前置条件。

### 为什么不做自动 RAG/向量库

材料一般很短，要求“按编号读取原文”和“逐字核对”，关键词检索 + 全文索引比向量检索更可解释。参与者也能调用工具读取完整段落。代价是长材料的语义召回有限。

### 为什么强制两位参与者都发言

“两位参与者从不同角度解读”是产品要求。若主持人可以只点一个人，三角色会退化为单角色聊天。因此服务端在主持人要结束或重复点名时做硬校验，提示主持人换人；这不是替主持人写台词。

### 为什么不做“必定反对”

参与者可以同意、补充、让步或修正。只有材料不支持时才明确说不足；不为了戏剧性强迫反方。总结保留未解决分歧，不强求和稀泥。

## 8. 已知限制

- 真实模型输出质量决定讨论质量；项目对结构、引用和状态规则做校验，但不保证推理、总结与课堂建议正确；
- 模型必须支持工具调用；不支持时可能失败并显示错误；
- 长材料只做关键词选段，不做完整语义索引；
- 没有 PDF 解析、语音、联网、多人、云同步；
- 总结仍是 AI 生成，不是事实核查；
- 已完成上述 qwen-plus 人工真实运行案例；自动化实模验收仍未完成。2026-11-04 浏览器 E2E 使用测试替身，不能当作真实模型证据。
